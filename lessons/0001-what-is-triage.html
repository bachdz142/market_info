What Is triage?

Lesson 1 · tied to: deciding how to configure this repo's engineering skills

Why this lesson exists: you're mid-way through setup-matt-pocock-skills, and the tool skipped the triage-labels section because triage isn't installed. Before deciding whether to install it, you should know what it actually does.

The one-line version

triage works through issues you didn't create — raw bug reports, feature requests, an unannounced external PR — and moves each one through a small state machine, ending in an agent-ready brief, a specific question for the reporter, or a closed issue with a reason recorded.

That "you didn't create" clause is the whole boundary. Issues that came out of your own planning (via to-spec → to-tickets) are already agent-ready by construction — running triage over them is wasted work. triage is the front door for work that arrived from outside.

It recommends and waits

This is the detail that separates it from labelling issues by hand: it tells you its category and state call, with reasoning, plus what it found in the codebase — and applies nothing until you direct it. Before any recommendation, it actually checks the claim: reproduces a bug from the reporter's steps, or checks out a PR's branch and runs the tests. The outcome is always one of three things — confirmed, failed to reproduce, or not enough detail to try.

The state machine

Every triaged item ends up with exactly one category role and exactly one state role — never zero, never two in conflict. Full table lives in the reference glossary; the shape to remember is:

StateMeans
needs-triageDefault landing spot — you need to evaluate it
needs-infoWaiting on the reporter
ready-for-agentFully specified, brief attached
ready-for-humanSame brief, plus why a human must do this one
wontfixClosed, reason recorded

wontfix is the one with texture: it splits into already implemented (comment only), rejected bug (polite close), and rejected enhancement (written to .out-of-scope/ — one file per rejected concept, so a future "night theme" request matches an existing dark-mode.md instead of starting the argument over).

Where it sits among the other skills

This is the part most people get wrong at first — triage is an on-ramp, not a step in the main chain. The main chain is work you originated: grill → spec → tickets → implement → review. triage is the parallel lane for work that arrived instead. Both lanes merge at the same place: an issue labelled ready-for-agent.

You haveReach for
A tracker full of raw reports from other people/triage
A rough idea of your own, nothing written downgrill-with-docs
A settled conversation ready to become a specto-spec
A confirmed bug needing a root cause, not a labeldiagnosing-bugs

One thing worth sitting with, given your repo

Market Insight Agent is currently a solo project. triage's entire reason for existing is inbound reports from other people. If nothing lands in your tracker except your own planning, you would rarely open it — the doc says this outright: "if everything in your tracker came out of your own planning, you will rarely open it." Worth keeping in mind as you finish the setup flow.

Retrieval practice — answer from memory before revealing.

1. How many state roles can one triaged issue carry at once?

Reveal
Exactly one, always.

2. Of the three wontfix reasons, which one writes to .out-of-scope/?

Reveal
Only the rejected enhancement.

3. Should you run triage over tickets that came out of your own to-tickets run?

Reveal
No — they're already agent-ready.

4. What does triage do before recommending anything?

Reveal
Verifies the claim actually holds.
