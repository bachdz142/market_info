# Collaborator-Friendly Source & Fetcher Architecture

Status: ready-for-agent

## Problem Statement

The user wants other collaborators to be able to add their own market-intelligence sources — and, where a source needs it, their own bespoke site-fetching logic — without stepping on each other's work or needing to reverse-engineer scattered conventions from scratch. Right now the full list of configured sources lives in one large file, and every piece of custom fetch logic lives in another single large file, both of which everyone editing any source has to touch. Adding one source that needs custom logic currently means editing the custom-fetch file in three separate places (a URL constant, a fetch function, and a line in a growing conditional dispatch chain — duplicated in two places depending on which processing path the source uses) plus the source-list file once. This scattered wiring already produced a real, silent bug: a custom fetch function wired into only one of the two dispatch paths, so the source quietly ran through the wrong, generic extraction path instead of its intended custom logic, with no error raised.

## Solution

Split the two monolithic files into small, focused modules organized the way a collaborator would actually think about the work — by content Layer for the source list, and by site/institution for custom fetch logic — reassembled automatically into the same collections every existing part of the codebase already expects. Replace the manual, two-places-to-edit conditional dispatch with a single, explicit registration step performed right where each custom fetch function is defined, declaring both the URL it handles and which processing shape it produces. Add a fast, offline, structural check that catches a mismatch between a registered fetch function's shape and its source's own configuration automatically, on every change, rather than relying on a human to notice. Add a short guide pointing collaborators at the decision ("does this need custom code, or does the existing declarative configuration mechanism already cover it?") and at one real, already-well-commented example, rather than an abstract fill-in-the-blank template.

## User Stories

1. As a new collaborator, I want to add a new source's configuration in a small, focused file, so that I don't need to read or understand the entire list of existing sources first.
2. As a collaborator working on sources in one content Layer, I want my changes isolated to that Layer's own file, so that my work doesn't conflict with someone else adding a source in a different Layer at the same time.
3. As a collaborator adding a source for a site the project doesn't yet have custom fetch logic for, I want to create one new, dedicated file for that site, so that everything related to fetching from it lives in one findable place.
4. As a collaborator adding another source for a site the project already has custom logic for, I want to extend that site's existing file, so that I can reuse constants and helpers already proven for that domain (request pacing, JS-wait conditions, content selectors) instead of duplicating them.
5. As a collaborator registering a new custom fetch function, I want one single, obvious registration step, so that I don't have to remember to wire it into multiple separate dispatch locations by hand.
6. As a collaborator registering a custom fetch function, I want the processing shape (a single combined document, versus a list of separately-processed pieces) to be a required, explicit part of registering it, so that a shape mismatch is structurally harder to introduce in the first place, not just caught after the fact.
7. As a maintainer, I want a fast, offline check that runs on every change, so that a fetch function registered for the wrong processing shape is caught immediately instead of silently degrading a source's output in production.
8. As a maintainer, I want the existing real-network, real-cost test suite left untouched and still something run deliberately, so that routine structural changes to source/fetch code don't require spending real fetch or LLM budget just to validate.
9. As a new collaborator, I want a short guide explaining when a source needs custom fetch code versus when the existing declarative site-configuration mechanism already handles it, so that I don't default to writing custom code for a case that's already covered.
10. As a new collaborator reading that guide, I want it to point me at one real, already-well-commented example rather than an abstract template, so that I can see the actual reasoning behind a real decision, not just fill in blanks.
11. As a developer relying on the existing source list and fetch functions elsewhere in the codebase, I want every current caller to keep working with zero changes, so that this refactor doesn't ripple into unrelated parts of the system.
12. As a maintainer, I want the total number of configured sources and their identifiers to be identical before and after the split, so I have concrete confidence nothing was silently dropped or duplicated during the migration.
13. As a maintainer, I want the simple, declarative, non-code path for straightforward sites to remain exactly as it is today, in one place, so that trivial additions stay trivial and aren't forced through the heavier custom-module process.
14. As a collaborator, I want each source's extraction prompt to remain exactly where it is today, defined alongside the rest of that source's configuration, so that adding a source and writing its prompt stay one unified step, not split across files.
15. As a maintainer, I want this refactor to explicitly avoid restructuring how prompts are authored or shared, so that the already-identified, separate future effort to improve prompt design isn't accidentally folded into a file-layout change.
16. As a collaborator debugging a source that isn't returning expected results, I want to be able to quickly tell whether its custom fetch function is registered with the correct processing shape, so that I don't waste time debugging the wrong layer of the system.
17. As a maintainer, I want the domain glossary to gain clear, distinct terms for "a source needing bespoke fetch code" versus "a source fully handled by declarative configuration," so future documentation and discussion about sources use consistent, unambiguous language instead of drifting to ad hoc phrasing.
18. As a collaborator new to the project, I want the migration to preserve source-control history where practical for moved code, so I can still trace the original reasoning and comments behind a piece of fetch logic.
19. As a maintainer, I want a handful of real sources spanning every processing category (plain declarative, custom single-document, custom multi-piece) verified to produce identical output after the migration, so I have concrete, not just theoretical, evidence the refactor didn't change behavior.
20. As a maintainer, I want every source's existing content-Layer classification preserved exactly as it is today, so the new file layout is purely organizational and doesn't require re-deciding any source's classification along the way.
21. As a collaborator, I want the site-level declarative configuration mechanism (for sources that don't need custom code at all) to stay untouched by this refactor, so I'm not asked to evaluate a second, simultaneous redesign while trying to add a source.
22. As a maintainer, I want the registration mechanism itself to be simple enough to explain in one sentence, so it doesn't become the next thing a new collaborator has to reverse-engineer.

## Implementation Decisions

- The single, large collection of configured sources is split into several smaller modules, organized along the project's existing content-Layer boundaries (the classification every source already carries), and reassembled at import time into the same single collection every existing consumer already depends on — no consumer elsewhere in the codebase needs to change.
- Custom, site-specific fetch logic currently concentrated in one large module is split into one module per site/institution, since a given site's several fetch functions typically already share constants and helper state (request-pacing keys, wait conditions, selectors) — splitting further, to one file per function, would only force re-importing that shared state across files.
- The current practice of manually adding a conditional branch per URL to route it to a custom fetch function is replaced by an explicit registration performed at the point each custom fetch function is defined. Registration declares two things: the URL the function handles, and which of two processing shapes it produces — a single combined document, or a list of separately-processed pieces.
- The dispatch logic that currently contains the manual per-URL conditional branches instead performs a single lookup against the set of registered custom fetch functions for a given URL. When no registration exists for a URL, behavior falls through to the existing generic, configuration-driven extraction path exactly as it does today — that fallback behavior is unchanged.
- The existing declarative, configuration-driven extraction mechanism (used for sites that need no custom code — just a content selector, an optional JS-wait condition, an optional document-link selector) is untouched by this work and keeps its current single, shared location and structure.
- Per-source extraction prompts remain exactly where they are today, defined as part of each source's own configuration entry — no extraction into separate files, no shared templating introduced by this work.
- The domain glossary gains two new, precisely defined terms as part of this work: one naming a source whose fetch logic requires a bespoke, site-specific function (because the declarative mechanism can't express what the site needs — an API call, a click-through interaction, page-range slicing of a document, etc.), and one naming a source fully handled by the declarative mechanism with no custom code at all. Both terms get recorded in the project's domain glossary once agreed, per the project's own convention of resolving vocabulary as it's decided rather than upfront.
- A short contribution guide is added, explaining the decision a collaborator needs to make first ("does this source need a custom fetch function, or does the declarative mechanism already cover it?"), the two resulting paths (add a configuration entry only; or add/extend a site-specific module and register a function, then add the configuration entry), and pointing at one real, already-existing, well-commented example rather than a synthetic fill-in-the-blank template.
- Every public function and the source collection itself that other parts of the codebase already import keep their existing names, call signatures, and observable behavior. This refactor is internal to how source configuration and custom fetch logic are organized and dispatched; it does not change any external interface.

## Testing Decisions

- A good test here verifies only externally observable behavior, not the internal file layout: that the full set of configured sources and their identifiers is unchanged after the split (same count, no duplicates, none silently dropped), and that every registered custom fetch function's declared processing shape actually matches what its corresponding source's own configuration says it should be.
- A new, fast, fully offline test asserts the core invariant this refactor exists to protect: for every registered custom fetch function, if it's registered as producing a list of separately-processed pieces, the source it belongs to must be configured to expect that; and vice versa for the single-document case. This test touches no network and can reasonably run on every change, unlike this project's real-network source tests.
- The project's existing real-network, real-LLM-cost test suite (which already exercises every configured source end-to-end) is left completely untouched by this work and remains something run deliberately rather than automatically — matching how it's already treated today.
- Prior art for the new test's spirit — fast, structural, no live dependency, safe to run by default — comes from this project's other existing offline-safe tests, which are already run routinely without touching the network or spending LLM budget.
- As a manual verification step alongside the automated test, a small number of real sources spanning each processing category (declarative-only, custom single-document, custom multi-piece) are exercised through the existing public fetch interface and checked for identical output to before the migration — following this project's existing convention of a no-LLM-cost fetch check before trusting a source's behavior.

## Out of Scope

- Restructuring, extracting, or templating per-source extraction prompts — a distinct, already-identified future effort, deliberately not folded into this file-layout and dispatch-mechanism change.
- Any change to the declarative, configuration-driven extraction mechanism itself (used by sources needing no custom code) — it is not part of the problem this spec addresses and is left exactly as-is.
- Reclassifying any source's existing content-Layer assignment — the split onto Layer-based files is purely organizational and must not require re-deciding any source's classification.
- Any change to the public interface, names, or behavior that other parts of the codebase currently rely on.
- Building a fully worked, synthetic example or template file for new custom fetch modules — the contribution guide points at a real, existing example instead.

## Further Notes

- This spec was scoped through a structured, round-by-round interview covering seven concrete architectural decisions (source-list split shape, fetch-module split shape, dispatch-replacement mechanism, whether the declarative configuration mechanism also needs splitting, whether prompts move, what the contribution guide looks like, and what the new structural test actually asserts), each resolved with the user's explicit agreement before being written up here.
- The motivating incident behind this whole effort was a real, already-experienced bug during this project's own development: a custom fetch function was registered for only one of the two possible processing paths a source could be routed through, and the mismatch produced silently degraded output rather than a visible failure. The new structural test exists specifically to catch this exact class of mistake automatically going forward.
- Preserving source-control history for moved code during implementation is a nice-to-have, not a hard requirement — it shouldn't block the migration if it can't be done cleanly for every piece of code being relocated.
